# 确认与下单

## 一、意图分流

| 意图 | 行为 |
|---|---|
| 只推荐 | 输出方案后停在这里，末尾附一句让用户回复序号的提示 |
| 要下单 | 输出方案的同时主动给出确认提示，用户确认后立即推进 |
| 定时推送 | 强制按只推荐处理，只给回复式入口 |

即使用户开口就要下单，也必须先展示明细再确认。意图决定的是要不要主动把用户带到这一步，不是能不能跳过确认。

## 二、确认的判定

明确肯定才算确认。以下一律不算：

```
试试看、如果可以就、可以就、随便你、你看着办
```

## 三、确认过期自动续期

展示的方案十分钟内有效。过期后不要求用户重新提问，自动用原参数重算一次：

- 价格没变则自动继续，不打断
- 价格变了则重新展示并重新确认

## 四、信任模式

默认关闭。用户明确要求"这个方案以后都可以直接下"时才开启，且必须同时满足三个条件：

```
1. 实付不超过档案中的额度上限
2. 门店在白名单内
3. 不动用积分
```

超出任一条件即退回普通确认。**积分消耗始终逐笔单独确认，信任模式也不豁免。**

## 五、建单

`create-order` 必填门店编号、订单类型、业务类型与商品列表。条件必填：

```
beCode          非自提时必填
takeWayCode     订单类型为一时必填，取自算价返回的 takeWayList 的 code
addressId       订单类型为二时必填
needTableware   是否需要餐具，默认不要
remark          外送备注，不超过五十字
```

建单只创建待支付订单。**任何情况下都不代用户支付。**

## 六、订单回执

是否返回支付链接尚未验证。无链接时输出订单号与在 App 或小程序完成支付的入口；接口确实返回了链接才展示链接。

不得输出预计配送时间——已验证的接口里没有这个字段。

回执措辞必须是"订单已创建（待支付）"。写成"订单已创建成功"会被读成已经买好了。

## 七、幂等

同一方案在确认后只建单一次。重复收到确认时先查询是否已有对应订单，已有则直接返回该订单，不重复创建。

## 七·五、建单异常必须先查后重，不可直接重试

**超时与报错都不代表没建成。** `create-order` 是写操作，请求发出后即使本地没收到响应，服务端也可能已经建单。直接重试会生成重复的待支付订单，用户可能付两次。

正确的处理顺序：

```
1. 先查   用 order-list 拉最近订单，比对门店、商品构成、金额、创建时间
          是否有本方案对应的那笔
2. 命中   已生成 → 直接拿该订单的支付入口返回给用户，告知「订单已存在，请支付这一笔」
3. 多笔   发现同一方案的重复未支付订单 → 用 cancel-order 取消多余的那几笔，
          只留最早一笔，并告知用户已清理。
          取消原因码传 2（重复下单）——这是接口的既有取值，不是自造的
4. 未命中 确认没有生成 → 征得用户明确同意后再重新建单，且只重试一次
```

判据用「门店 + 商品构成 + 金额」三元组，不要只看金额：同一门店同金额的不同单可能是用户自己下的，误当成自己的订单会导致漏单。

**任何情况下都不允许「失败即重试」的裸循环。** § 八 的「不重试超过两次」指的是只读接口（算价、券查询）的容错上限；对 `create-order` 这个写接口，重试的**前提永远是先确认上一笔不存在**，且重新建单必须经用户点头。

## 八、失败兜底

| 情况 | 处理 |
|---|---|
| 商品售罄 | 剔除该商品重新生成候选并重新算价 |
| 券不可用 | 剔除该券重新排序，不中断 |
| 复价结果不一致 | 回到确认环节重新确认，不许用新值直接下单 |
| 建单失败或超时 | **先按 § 七·五 用 order-list 查是否已生成**，命中就直接复用，未命中才经用户同意重试一次；不做裸重试 |
| 算价回显异常 | 该候选作废不入排序；全部异常则停止并说明，不输出任何金额 |
| 网络超时 | 重试两次后进入降级，说明当前无法下单 |
