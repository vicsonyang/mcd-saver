# 算价与最优组合

## 一、目标函数只有一个

```
min( data.price )
```

`data.price` 已包含商品价、配送费、打包费与餐具费。最小化它，就是四者的联合最优。不需要为配送费单独设计机制。

在本地不做任何价格推算。所有实付价一律以服务端返回为准；本地估算只能作为排序参考，并标注为推断，不得当作实付展示。

## 二、禁止向接口传契约外字段

`calculate-price` 与 `create-order` 的入参清单是封闭的，传未定义字段会被直接拒绝，而不是被忽略。以下都会被拒：

```
{ ..., usePoints: true }
{ ..., pointsDeduction: 500 }
{ ..., autoSelectBestCoupon: true }
```

积分没有对应的算价入参，只能通过兑换成券再参与算价。

## 三、候选生成

四个可选参数，一律不强制用户提供。其中人数单独处理，其余三项缺哪一项就降级到下一级来源：

| 参数 | 含义 | 缺省时 |
|---|---|---|
| `people` | 人数 | **用户没说时按一人处理**，不读档案，也不按常点清单里的份数推断 |
| `budget` | 预算上限（元） | 无则不设上限 |
| `meal_preference` | 口味与品类偏好 | 退到服务端常点清单 |
| `exclude` | 忌口清单 | 取档案忌口表，缺省为空 |

**人数为什么单独处理**：其余三项缺了只是猜得不够准，人数缺了会直接决定买几份主食，错了整单都错。所以人数不设「降级到档案」这一级——档案里的人数是历史值，与用户此刻几个人吃没有关系，按它推断等于拿旧数据冒充当前需求。

偏好来源优先级：用户本次明说，高于服务端常点清单，高于本地档案。**此优先级不适用于人数。**

可执行规则：

- 人数换算件数：单人一份主食加零到一份小食加零到一份饮品；双人两份主食加一份小食加一到两份饮品；三人及以上优先多人分享餐类目
- 按一人处理时，在方案末尾附一句提示，说明本次按单人量选、说一声即可改成多人
- 忌口按商品名称与类目关键词剔除
- 命中冷饮、咖啡、纯牛肉、超值等标签时，同价方案优先推
- 剔除棒球帽、痒痒挠等非餐饮商品
- 券失效时对应组合一并剔除

**最终呈现最多三个候选**，避免选择困难。算价阶段可以多试几个组合，但给用户看的只留三个：实付最低的、含目标商品的、以及性价比最高的加购项。

数量纪律：

```
呈现上限        三个。超出的不展示，描述为「已比对的其余组合」一句带过
低于三个        先检查是否剪枝过度；确实只有一两个可用组合时，如实给一两个，凑数禁止
候选必须贴合需求  用户明说了目标商品（如「我想吃巨无霸」）时，只推含该商品的组合。
                同类目但不同款的商品（如「不素之霸双层牛堡」对「巨无霸」）不算命中，
                不得因凑数量而混入。数量不够就少给，不许拿无关项填空
```

**判定「是否含目标商品」必须看套餐详情，不能只看类目名。** 类目名（如「巨无霸 牛鱼肉堡」）会把多款产品归在一栏，名称带「牛」的套餐（牛气满满、不素之霸）主堡都不是巨无霸。要确认含不含，调 `query-meal-detail`（参数名 `code`）看 `rounds[].choices`，或直接看算价返回的 `productList[].productName`。

## 四、预算过滤分两段

生成阶段用菜单现价粗筛，剔除明显超预算的组合，避免浪费算价调用。算价之后用实付价硬过滤，实付超过预算的组合丢弃。

**绝不能用原价做硬过滤**——原价超预算、用券后正好落入预算，正是本 Skill 最该命中的场景，误杀即本末倒置。配送费可占订单近两成，用原价筛会系统性误判。

全部候选都超预算时不许空手输出：给出实付最接近预算的组合，标注超支金额，附一条可选补救建议，并说明当前预算下无可行方案。

## 五、凑单

依据 `enjoyable.balance`（还差多少分享受优惠）做确定性决策，不试探：

```
1. 差额大于零且不超过凑单上限时，挑价格最接近差额的低单价小食
2. 净收益 = 跨门槛后的优惠增益 − 凑单商品成本
   净收益大于零 → 采纳，标注凑了多少、省了多少
   净收益小于等于零 → 不采纳
3. 反向校验：用券或积分兑换后，商品额可能跌破免配送费门槛，
   导致实付不降反升 → 必须重算一遍再比较，取真最优
```

第三步是券、积分与配送费三者真正联动的地方。把商品额压太低反而多付配送费，因此三者必须联合优化，不能各自求最优。

## 五·五、凑单陷阱：判定与提示

第五节讲的是「净收益 ≤ 0 就不采纳」。只做不采纳不够——用户看不到你替他挡掉了什么，下次他自己点还是会踩。**命中陷阱必须讲出来。**

两条判据，任一命中即为陷阱：

```
判据一 · 同构成换券
  商品清单完全相同、只有挂不挂券不同时：
  挂券的实付 ≥ 不挂券的实付 → 这张券对本组合没有价值

判据二 · 跨构成凑单
  凑单方案的实付 ≥ 「商品更少、实付不更高」的方案
  → 为触发门槛多买的那几件白买了，报出多买几件、多花多少钱
```

判据一只比「商品构成相同、仅券不同」的两两组合；判据二只在凑单方案上比。不要拿完全不同的商品组合互相比较，那会产生大量无意义的噪音提醒。

**提示话术必须带数字与对照方案**，不能只说「不建议凑单」：

```
为触发「满50减12」的门槛多买 1 件中薯条，实付 ¥45.00；
而「麦辣鸡腿堡 + 可乐 + 满20减3」商品更少、实付仅 ¥32.50。
除非你本来就想吃中薯条，否则不建议为用券而凑单。
```

按「多花了多少钱」降序，**最多保留三条**。没有命中就不写这一段，不硬凑。

## 六、排序

主目标只有一个，其余全是平局规则。

```
主目标：实付升序

实付相同或差额不超过一元时，依次比较：
1. 不动用积分优先于动用积分
2. 消耗临期券优先于远期券
3. 券的抵扣力度大者优先
4. 命中偏好优先
5. 满足人数、预算与忌口约束
```

券的力度、是否临期这类属性不能用来决定用哪张券。力度最大的券常常只适用于高价组合，与临期优先也会互相冲突；让它们做主目标会算出更贵的方案。

## 七、积分

积分不能在点餐链路直接抵现金，只能先在积分商城兑换成券，再作为普通券参与算价。

积分不足时跳过兑换，方案照常产出，并输出本月与下月将过期积分提醒。积分快过期却花不掉，比帮用户花掉更值得说。

积分充足时也**不**自动兑换，先过净收益判据：

```
净收益 = 该券在本单的实际抵扣额 − 这笔积分在积分商城的最优替代用途价值
净收益大于零才兑换
```

替代用途价值无法精确估计，落地为两条可判定规则：商城当前无可换商品时视为替代价值为零，兑换；有可换商品时，只有本单抵扣额显著高于同额积分能换到的最好那一件时才兑换。

积分消耗始终逐笔单独确认，任何模式都不豁免。

## 八、调用预算与失败兜底

算价是整条链路最耗时的一步，**先算多少、后算多少直接决定用户等待时长**。按下面的顺序分配，用完即停：

```
第一阶段 · 只算最终要呈现的裸单
  候选生成后先剪到最终呈现数量（默认三个），只给这三个各算一次裸单价，并发发起。
  不要为「可能有更优解」而把候选池全算一遍——候选池里的多数组合不会进最终呈现，
  算了就是白算。裸单必须参与排序，挂券不等于更省

第二阶段 · 只给实付最低的那一个挂券
  取实付最低的候选挂一张券重算，只做一次。
  注意：挂券后实付通常升高（券是加购型），所以这一步是为了确认最优候选是否仍最优，
  不是为了找更便宜的裸单

第三阶段 · 叠加一律不试
  上界恒为一，两张同时挂必定返回 600022。无需试探，直接跳过
```

**算价次数固定为 4 次**（3 次裸单 + 1 次挂券），下单前的复价只复最终确认的那一个方案，另计 1 次。不为第二、第三名候选各挂一次券——那两次只影响备选方案的「多花 X 换 Y」精确值，不改变最低价结论，却要多等两轮。

备选方案因此**不写精确的「多花 X 换 Y」数字**；需要比较时按 1/5 判据给「约」值，并注明未经单独核价。用户主动要求改搭配、或某候选被剔除需要补位时，再追加算价，总次数仍不超过八次。

券数量大于一时，只试抵扣额最高的那一张。

**并行发起的边界**：`calculate-price` 之间若互不依赖（都是独立组合），应当在同一条消息里并发发起，不要串行等待。只有需要根据上一步结果才能决定的组合（如「先看谁最便宜，再给它挂券」）才串行。

同一接口最多重试两次，之后永久降级。全部算价失败则停止，不输出任何金额。部分失败时只在成功组合里排序，并标注本次比对了 N 分之 M 个组合。

## 八·五、回显必须校验，不能盲信返回值

服务端返回成功不等于这单是对的。**算价返回的 `productList[]` 必须与本轮请求的 `items[]` 逐项核对**，核对不通过的报价一律作废，不能进入排序，更不能拿去下单。

四条校验，任一条不通过即作废该候选：

```
1. 数量一致      每个 productCode 的 quantity 必须与请求完全相同。
                 请求 2 份回显 1 份，说明该商品被合并或限购，价格作废
2. 无凭空商品    productList 里不得出现请求中没有的商品。
                 唯一例外：菜单 discountType 以「随单购」开头且请求带了 withOrder 时，
                 回显会多出一行卡商品，属正常，其小计已计入 data.price，不得另加
3. 券确实生效    请求挂了 couponId 时，回显的优惠应体现为对应商品小计下降。
                 若小计与原价相同（券没生效），该候选按「无券价」重算，不能按挂了券报
4. 金额自洽      data.price 应等于商品小计 + 配送费 + 打包费 + 餐具费 − 优惠。
                 对不上说明字段读错（如把分当成元），先查单位再决定是否作废
```

作废的候选要记录原因，并在搜索过程行里如实计入「官方核价 J 个候选」的分母，同时用一句话说明「其中 X 个回显异常已剔除」。**不得把作废的候选悄悄从分母里减掉**，那会让核价数量看起来比实际少。

**加购型券的判定也要靠回显**：把券挂上后实付上升、且上升额等于券商品的原始单价，说明这是加购型券（只让加购商品变便宜，不降低原订单），不是减价型。此时必须按「实付增量」而非「抵扣额」向用户表达。

## 九、下单前必须复价

用完全相同的参数再算一次。结果与展示值不一致时，必须回到确认环节重新确认，不许默默用新值下单。
