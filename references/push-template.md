# 每日推送

## 一、为什么值得做

券呈每日一张不同的排布，且各自绑定星期与时段。今天最划算的答案每天都不一样，所以每日推送是真需求。

建议在午餐餐段开始前推送，此时券与餐段都已就位。

## 二、必填字段

```
pushId / pushedAt / expiresAt    推送标识、服务器时间、方案失效时间（默认加十分钟）
storeName / storeCode / channel  门店必须显式展示
locationSource                   门店来源：用户明说／按地址搜索选定／档案默认
plan.price / originalPrice / discount   实付、原价、优惠
plan.feeBreakdown                配送费、打包费、餐具费、商品费四项拆解
plan.items[] / plan.coupons[]    商品清单；券名加有效期加时段
plan.pointsUsed / evidenceLabel  积分消耗；证据标签
expiringSoon[]                   三天内到期券（含三态与面值合计）、今天到期的券，
                                 以及本月将过期积分提醒
nextAction / optOutHint          行动指令必须为确认式；退订说明
```

定时推送时门店来源通常为「档案默认」。此时门店行必须带警示标记，
说明门店来自档案、未经核对，若不在该门店附近需回复新地址重算。

## 三、三条硬约束

1. **绝不自动下单**。只给回复式入口，用户回复序号后先复价再建单
2. 算不出就推算不出，不推基于估算的假价格
3. 连续三天无响应降级为纯文字摘要，减少算价调用；连续七天无响应提示是否退订

## 四、回复序号的处理

用户回复序号后，先用保存的方案快照重新算价：

- 价格一致则直接推进到确认环节
- 价格变了则展示新价格并重新确认

这样兼顾速度与安全：用户不必重新描述需求，也不会按过期价格下单。

## 五、任务配置

定时能力由宿主的自动化能力提供。宿主不支持定时时，改为用户手动发起，不谎称已配置定时推送。
