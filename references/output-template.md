# 输出模板

三套模板，字段不得增减，只调整详略。

## 模板一 · 对话场景

正文之前必须先有**券汇报行**与**门店行**，顺序固定，不可省略：

```
（券汇报行）
（门店行）
（候选正文）
```

### 券汇报行（必须在最前面）

先说本次领券情况，用户才知道我做了什么。三种情形选一种，不得含糊：

```
领到券了     麦麦省已帮你领到 2 张券：麦麦省15元券、中薯条买一送一（有效期至 10-16）
没领到       麦麦省本次没有可领的券；你现在能用的是：中薯条买一送一、王牌小食拼、9.9元中杯冰美式
一张都没有   麦麦省本次没有可领的券，你当前也没有可用券
```

四条硬规则：

```
1. 领到几张就报几张。领到零张时禁止写「已为你自动领券」，那是不实陈述
2. 没领到时必须列出卡包里现有哪些券——这是「没领到」与「什么都没有」的区别，
   用户需要知道手上还有什么牌可打
3. 券要带上有效期。有效期从领取那一刻起算，不说清楚用户会错过
4. 手上有券时顺带给到期与面值汇总，三态分清、口径写对
```

第 4 条的写法：

```
有券要到期    其中 2 张将在 3 天内陆续过期，面值合计 ¥14.50（不用掉就等于损失）
今天有到期的  今天到期 1 张（面值 ¥9.90），今天不用就作废
有券不过期    手上有 2 张券，暂无近期到期的
```

面值按商品名去菜单反查：满减券取减免额，买一送一取该商品单价，固定价券取「原价 − 固定价」；**反查不到的券标「价值未知」，不估算。**
这一行是**到期损失**的口径；本单省了多少仍按实付增量写在候选正文里，**两个口径不得混写**。

**没领到但手上有券时，要顺带说明这些券是否值得用。** 本 Skill 的券多为加购型，挂了只会加价，若如此就直说「这几张都是加购型，不挂反而更省」，别让用户以为有券就该用。

### 门店行

**门店行按来源三选一，不可省略**：

```
用户明说    广州华丰汇店 · 麦乐送（按你指定的门店）
搜索选定    广州华丰汇店 · 麦乐送（按你给的地址搜到的最近门店）
档案默认    <档案中的门店名> · 麦乐送（⚠️ 门店来自档案，未与你的实际位置核对）
```

档案默认这一种必须带警示标记。它意味着门店可能与用户当前位置无关，整单推荐可能因此作废。

**门店与收货地址是两条独立信息，绝不能拼进同一行。** 麦乐送场景下门店负责出餐、地址负责送达，两者没有从属关系。把地址塞进门店行会让用户以为该地址就是门店所在地：

```
错误   华丰汇店 · 麦乐送（按你上次指定的门店，地址：<收货地址>）
       —— <收货地址>是收货地址，与华丰汇店的门店地址无关

正确   华丰汇店 · 麦乐送（按你上次指定的门店）
       送到：<收货地址>（账号默认地址）
```

因此门店行写完后，**收货地址另起一行**，并标明它的来源：

```
明说地址     送到：广州市XX路XX号（你指定的地址）
授权/档案地址 送到：<账号默认收货地址>（账号默认地址，如需送别处请说明）
到店自取     无需地址；改为标明取餐方式（到店自取）
```

地址来源是账号默认而非用户本次明说时，要加「如需送别处请说明」，给用户一个低成本纠正的机会。

### 候选正文

```
【方案一 · 推荐】应付 ¥48.50 ｜ 实付 ¥28.50（省 ¥20.00）
  商品 ¥22.50 ｜配送 ¥0.00（原价 ¥6.00，已减免）｜打包 ¥6.00 ｜餐具 ¥0.00
  构成：巨无霸 ×1 ＋ 中薯条 ×1 ＋ 中可乐 ×1
  用券：麦麦省15元券 −¥15.00（今日可用 10:30-23:59，剩 7 天）
  积分：未使用（可用 12.5 分，本月将过期 8 分）
  证据：已验证（服务端返回）

【方案二】应付 ¥44.00 ｜ 实付 ¥44.00 —— 想多吃一份主食，选这个
【方案三】应付 ¥36.10 ｜ 实付 ¥36.10 —— 完全不用券

※ 价格已含配送/打包/餐具费；下单前会重新算价，以重算结果为准
回复「1」（或「1 到店」／「1 送到本地址」），我先给完整明细再建单。
```

### 提醒段（命中凑单陷阱时必须写）

**命中就写，没命中整段省略**，不硬凑。判据两条，任一命中即为陷阱：

```
判据一 · 同构成换券
  商品清单完全相同、只有挂不挂券不同时：挂券的实付 ≥ 不挂券的实付
  → 这张券对本组合没有价值

判据二 · 跨构成凑单
  凑单方案的实付 ≥ 「商品更少、实付不更高」的方案
  → 为触发门槛多买的那几件白买了，报出多买几件、多花多少钱
```

```
⚠️ 需要提醒你
为触发「满50减12」的门槛多买 1 件中薯条，实付 ¥45.00；
而「麦辣鸡腿堡 + 可乐 + 满20减3」商品更少、实付仅 ¥32.50。
除非你本来就想吃中薯条，否则不建议为用券而凑单。
```

三条要求：

```
1. 必须给出对照方案与两个实付金额，不能只说「不建议凑单」
2. 按「多花了多少钱」降序，最多三条
3. 未命中陷阱时不写这一段，也不写「本次没有凑单陷阱」这类空话
```

### 搜索过程行（必须在候选正文与提醒段之后、确认话术之前）

**这一段是给用户看的证据，不是技术日志。** 用户看完三个方案后，第一个疑问永远是「你是不是真比过了、有没有更便宜的没算」。只写「已比对的其余组合」等于没说，必须把实际做过的工作量摊开：

```
翻本店 N 款菜单 ｜ 拆开 M 个套餐看全部可选项 ｜ 本地比较 K 种点法 ｜ 官方核价 J 个候选
```

四个数字都必须来自本轮真实调用，不得估算、不得沿用上轮数字：

```
翻本店 N 款菜单      query-meals 返回的 meals 映射表条目数
拆开 M 个套餐        本轮实际调 query-meal-detail 的次数
本地比较 K 种点法     按菜单价推算过的组合数（不必全部提交算价）
官方核价 J 个候选     本轮实际发起 calculate-price 的次数（含失败的）
```

行尾要接一句结论，把「省了多少」量化。有两种比法，按用户有没有点名商品选：

```
有目标商品  你要的这杯麦旋风 ¥16.50，最省的点法是 ¥32.35 拿两杯（摊薄后每杯 ¥16.20）
无目标商品  同样这些东西全按单点买要 ¥87.50，最省的方案 ¥59.80，少花 ¥27.70
```

**「多花 X 换 Y」的量化判据**：

```
判据        多花金额 ≤ 多得商品单点原价的 1/5 时，才值得单独列出来
多花金额     该方案实付 − 最低实付方案的实付（正数）
多得商品原价  两方案商品清单之差，按单点原价合计
等号情形     恰好等于 1/5 也算值得，列出
不满足       不列，或列了必须标注「不划算」，不得暗示成优惠
```

**备选方案的「多花 X 换 Y」只算一次挂券，不一定有精确值。** 算价只给实付最低的候选挂券，备选方案没有单独核过价时，这两个数字只能给「约」值并注明未经单独核价，不得写成精确值。

例：多花 ¥9.90 多得一杯原价 ¥19.00 的冰美式 → `9.90 ≤ 19.00 ÷ 5 = 3.80`？不成立，所以这条只能作为「你想喝咖啡就顺手加」的中性建议，**不能写成「很划算」**。反过来，多花 ¥1.00 多得一份原价 ¥5.00 的薯条 → `1.00 ≤ 1.00` 成立，可以推。

本 Skill 没有随单开卡场景时，不必计算卡费比价；一旦菜单出现 `discountType` 以「随单购」开头的商品，须把「不开卡」与「开卡含卡费」两种整单实付都算一遍再选低的。卡的价值按 ¥5.00 计，不超过实际卡费。

**结尾确认话术必须让用户同时给出序号和渠道。** 渠道决定算价与门店，不在确认时问清就要在最后返工：

```
回复「序号」＋「到店」或「配送到本地址」，我先给完整明细再建单。

例  回复「1 到店」        → 到店自取
    回复「1 送到本地址」   → 麦乐送，送到账号里的默认地址
```

**渠道已定时只需序号。** 渠道在第 2 步定场景（用户明说或沿用历史）时已经确定，就不属于「未问清」的情形。此时确认话术退化为只要序号，渠道不再重复索要：

```
回复「1」「2」或「3」，我先用相同参数复价，一致就建单（到店自取 · 门店名）。
```

仍然只需序号的理由：渠道与门店都已经回过显，再问一遍是多余往返。两个条件同时成立才走这条退化话术——**渠道已确定** 且 **门店已随候选正文回显**，缺任一条件仍按上一段同时索要序号和渠道。

用户只给了序号没给渠道时，按档案 `defaultChannel` 继续，并在明细里标明用的是哪个渠道，让用户有机会纠正。不要反问他一次——他已经表达了要下单，再问一轮是多余往返。

## 模板二 · 定时推送场景

在模板一基础上加时间头部与退订尾部。券汇报行与门店行仍按模板一的规则写，不重复另起一行：

```
🍔 今日省钱方案 · <门店名> · 麦乐送
11:00 服务端实时试算 · 方案 10 分钟内有效
麦麦省已帮你领到 2 张券：麦麦省15元券（有效期至 10-20）

（门店行）
（候选正文）

回复「退订」可停止每日推送。
```

推送同样只给回复式入口，绝不自动下单。

## 模板三 · 订单回执

```
✅ 订单已创建（待支付）
订单号：xxxxxx
门店：<门店名> · 麦乐送
实付：¥28.50（已复价，与方案一致）
支付入口：请在麦当劳 App / 小程序「我的订单」完成支付
       （接口若返回支付链接，此处直接给出）

```

## 呈现三个候选的原则

候选清单**最多三个**，避免选择困难。三个的位置这样用：

```
主方案    实付最低的那个
备选一    含用户目标商品的另一条路径（如加一份饮品或小食）
备选二    想吃完整套餐的那条，或性价比最高的加购项
```

只有一两个可用组合时，如实给一两个，**禁止为凑满三个而混入无关商品**。超出三个的已算组合，用一句话带过（「另比对过 N 个组合，均更贵」），不逐条列出。

## 对比表固定列

多个候选并排展示时，固定四列，顺序不可调：

```
| 方案 | 构成 | 应付 | 实付 |
|---|---|---|---|
```

三条硬规则：

```
1. 应付与实付必须分列。应付=未用券时的金额（服务端 originalPrice / 100）；
   实付=用券后的 price / 100。两者相同时两列都写同一个数，不合并成一列
2. 实付 ≠ 应付时，实付金额后面紧跟括注省了多少：「实付 ¥45.50（省 ¥9.10）」
3. 构成列只写「商品名 ×份数」，用「＋」连接，不写券名、不写抵扣额、
   不写「单点」这类方式词。券的信息属于应付/实付两列和用券行
```

构成列正误对照：

```
正确   巨无霸 ×1 ＋ 中薯条 ×2
正确   培根蔬萃双层牛堡 ×1 ＋ 玉米杯(小) ×1 ＋ 无糖中可乐 ×1
错误   单点 + 券（抵扣¥9.10）        把券塞进构成
错误   牛肉汉堡套餐                    只写类目名，看不出里面有什么
错误   薯条 + 可乐                     漏了主堡
```

**构成必须写完套餐的全部子项**，包括默认选中的饮料和小食。子项来自 `query-meal-detail` 的 `rounds[].choices`（取 `isDefault=1`），或算价返回的 `productList[].productName`。只看 `query-meals` 的菜名会漏掉子项。

## 五条硬性排版规则

1. 金额一律两位小数。底层单位是分，28.5 必须写成 ¥28.50
2. 配送费必须分列原价与现价。只写一个数字会让人分不清是收了六元还是免了六元
3. 一个订单只写一张券。实测上界为一，多张并列必然算价失败；某张券未生效就不写，不猜原因
4. 领券结果按实际汇报。领到零张时不能写已为你自动领券，首次授权未完成时也不写
5. 不出现任何未经接口返回的字段，尤其是支付链接与预计配送时长
6. 加购型券必须写清实付增量。券只让加购的那件商品变便宜，不会让原订单降价，所以挂券后的实付通常高于裸单。必须同时给出"券抵扣多少"与"比裸单多付多少"，只写抵扣额会让人误以为总价降了

## 三项强制标注

```
计算口径    价格来源为服务端实时试算；标注算价时间、门店与渠道；
            必须写明含配送费、打包费与餐具费
门店来源    标明门店依据的是用户明说、按地址搜索选定还是档案默认；
            档案默认时附加未经核对的警示
券有效期    含星期时段限制，剩余不超过三天的重点提示；
            手上有券时附三态汇总与面值合计（见券汇报行第 4 条）
证据标签    已验证（服务端返回）／推断（仅排序参考，不得作为实付展示）／未验证
```

外加一句固定提示：下单前会重新算价，最终以重算结果为准。

## 算不出时怎么说

算不出就直说算不出，不推基于估算的假价格：

```
今天没能算出省钱方案（原因：优惠券接口暂时不可用）
已跳过本次输出，明天同一时间再试。
回复「立即重试」可现在再算一次。
```
